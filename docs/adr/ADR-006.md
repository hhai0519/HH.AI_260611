# ADR-006: 基於 Redis CAS 機制的狀態機版本控制

## 狀態
已通過 (Accepted)

## 背景
在無人類工程師常駐的多 Agent 分布式系統中，多個 Worker 或 Governance Engine 實例可能並發觸發狀態轉移。若無並發防護，可能產生狀態覆寫的競態條件，甚至導致狀態損毀 (State Corruption) 或系統腦裂。

## 決策
1. 將系統狀態變更納入版本化控制。在 Redis/DB 中將 `SYSTEM_STATE` 與 `state_version` (單調遞增的整數，初始化為 1) 綁定。
2. 狀態更新必須強制採用 Compare-And-Swap (CAS) 原子操作。
3. **技術實作**：使用 **Redis Lua script** 執行比對與更新。
   ```lua
   local current_version = redis.call('get', 'SYSTEM_STATE_VERSION')
   if tonumber(current_version) == tonumber(ARGV[1]) then
     redis.call('set', 'SYSTEM_STATE', ARGV[2])
     redis.call('set', 'SYSTEM_STATE_VERSION', tonumber(ARGV[1]) + 1)
     return 1
   else
     return 0
   end
   ```
4. 任何轉移請求若帶入的舊版本號與 Redis 端不符，將立即被拒絕，降低逆向覆寫的風險。此機制屬於核心穩定區，任何修改比照四道閥門辦理。

## 後果
- 降低併發更新覆寫和腦裂的風險。
- 對狀態寫入具備強原子性與順序防護。
- 維持了治理控制在程序上的一致性。
